# امکان‌سنجی Web Push

آزمایش فاز P0. صفحهٔ جدا: `/admin/push-lab` (فقط مدیر کل). کلید VAPID محلی است. `PUSH_PROXY_URL` روی این سرور تنظیم نشده، چون هر سه میزبان از خود سرور مستقیم در دسترس بودند.

تاریخ آزمایش سرور: ۱۴۰۵/۰۷/۱۵.

## دسترسی سرور

درخواست نمونه: `GET /` با TLS و timeout هشت ثانیه. کدهای ۴۰۴، ۴۰۵ و ۴۰۶ یعنی اتصال و TLS برقرار است و ریشهٔ سرویس متد یا مسیر را قبول نمی‌کند.

| میزبان | مستقیم | با پروکسی |
| --- | --- | --- |
| `fcm.googleapis.com` | DNS و TLS برقرار، HTTP 404، حدود ۵۶۷ms | لازم نشد؛ پروکسی تنظیم نشده |
| `web.push.apple.com` | DNS و TLS برقرار، HTTP 405، حدود ۸۵۰ms | لازم نشد؛ پروکسی تنظیم نشده |
| `updates.push.services.mozilla.com` | DNS و TLS برقرار، HTTP 406، حدود ۵۶۲ms | لازم نشد؛ پروکسی تنظیم نشده |

## ماتریس دستگاه

ستون «مستقیم» از سرور بدون پروکسی است. ستون «با پروکسی» تا وقتی `PUSH_PROXY_URL` خالی است قابل آزمایش نیست. خانه‌های خالی را بعد از تست گوشی پر می‌کنیم.

## پیشنهاد

مسیر خروجی سرور به FCM، اپل و موزیلا مستقیم باز است. تنظیم پیشنهادی فعلاً بدون پروکسی است: `PUSH_PROXY_URL` را خالی بگذارید. اگر در ماتریس دستگاه یک کانال اشتراک بسازد ولی ارسال مستقیم کد خطا بدهد، همان ارسال را با پروکسی تکرار می‌کنیم و این پیشنهاد عوض می‌شود.

تا نتیجهٔ دستگاه‌ها نرسد، هیچ کانالی «قابل اتکا روی گوشی» اعلام نمی‌شود. فقط می‌شود گفت سرور به هر سه سرویس push می‌رسد.
